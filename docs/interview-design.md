# 모의면접 구현 설계 (작성 중)

2026-10-29, 팀원(a77315829-byte 세션)이 정한 내용을 옮겼다. `docs/problem.yaml`의 solution_paths·features로 옮기기 전 단계의 설계 메모다.
팀 합의가 필요한 부분은 `progress.md`의 「합의가 필요한 제안」과 `docs/problem-revision-proposal.md`에 따로 적었다.

## 1. 전체 흐름

1. 로그인
2. 이력서 템플릿으로 정보 입력
3. 자소서가 없으면 → 입력한 이력서를 바탕으로 자소서 초안 생성 / 자소서가 있으면 → 등록
4. 그 자소서를 바탕으로 2:1 모의면접(면접관 2명 : 사용자 1명)
5. 면접 결과에서 설명이 부족한 부분 확인 → 자소서 보완

- 질문은 TTS로 읽는다. 답은 음성과 글자 입력 둘 다 받고, 같은 답변 처리 과정을 쓴다. 음성은 전사 내용을 사용자가 확인·수정할 수 있다.
- 백엔드는 NestJS, DB는 MongoDB, AI 모델은 `openai/gpt-6.1-terra`(2026-10-29 결정). 구현: `interview-engine/`.
- RAG(외부 문서 검색)는 쓰지 않는다. 사용자의 자료와 면접 상태를 AI 호출에 직접 넘긴다.

## 2. 면접관

| 면접관 | 본질문 수 | 확인 목적 |
| --- | --- | --- |
| 실무 면접관 | 2개 | 본인 기여, 문제 해결 과정·선택 이유·검증 방법 (직무에 관한 질문) |
| 임원 면접관 | 2개 | 협업 과정, 책임 있는 판단·실패 이후 행동 (인성에 관한 질문) |

- 임원 면접관도 구체적인 행동과 판단 근거를 묻는다. 답변으로 성격을 진단하거나 '인성이 좋다·나쁘다'고 판정하지 않는다.

## 3. 본질문 만들기

- 면접 시작 시 사용자의 이력서와 선택한 자소서를 넘기고, AI 호출 한 번으로 본질문 4개(실무 2·임원 2)를 만든다.
- 질문 문장은 자소서에 맞춰 달라진다. 사용자가 입력하지 않은 경험이나 성과를 전제하지 않는다.
- 질문마다 면접관, 확인 목적, 근거가 된 자소서 문장을 함께 저장한다.
- 질문 순서는 서버가 세션 생성 때 한 번 랜덤으로 정해 MongoDB에 저장한다. 새로고침해도 바뀌지 않는다.
- 질문 생성 실패에 대비한 기본 질문 템플릿을 둔다. 대체 질문을 썼다는 상태를 기록한다.

## 4. 진행 규칙

- 한 번에 면접관 한 명이 질문 하나만 한다.
- 꼬리질문은 그 본질문을 시작한 면접관이 계속 맡는다. 본질문당 최대 2개.
- 현재 주제가 끝나면 다음 순서의 면접관이 미리 만든 본질문으로 넘어간다.
- 두 면접관은 같은 답변 기록을 공유해 이미 설명한 내용을 반복해서 묻지 않는다.

| 항목 | 값 |
| --- | --- |
| 본질문 | 총 4개 (실무 2·임원 2) |
| 본질문당 꼬리질문 | 0~2개 |
| 전체 질문 수 | 최대 12개 |
| 진행 시간 | 최대 12분. 도달하면 현재 답변을 마친 뒤 종료 |
| 사용자 선택 | 언제든 질문 건너뛰기·면접 종료 |

- 질문 다시 듣기, 음성 인식 재시도는 질문 수에 넣지 않는다.
- 숫자는 구현·시연용 초기값이며 써 본 뒤 조정한다.

## 5. 꼬리질문 판단

답변에 점수를 매기지 않고, 항목별로 `설명됨 / 추가 확인 필요 / 모름·경험 없음`을 기록한다.

| 답변 상태 | 다음 행동 |
| --- | --- |
| 본인 역할이 불분명함 | 직접 담당한 부분을 묻는다 |
| 행동은 있지만 선택 이유가 없음 | 선택 기준을 묻는다 |
| 결과를 말했지만 확인 방법이 없음 | 결과를 어떻게 확인했는지 묻는다 |
| 이전 답변과 내용이 다름 | 두 설명을 보여 주고 어느 쪽이 맞는지 다시 확인 |
| 현재 질문의 확인 목적이 충족됨 | 다음 본질문으로 이동 |
| 모른다·경험이 없다고 답함 | 필요하면 한 번 쉽게 바꿔 묻고, 계속 어려우면 보류 |
| 꼬리질문 2개를 이미 씀 | 미해결 항목을 기록하고 다음 본질문으로 이동 |

- 답변이 짧다는 이유만으로 꼬리질문하지 않는다. 숫자가 없는 정성적 결과도 인정한다.

질문 생성 규칙:
- 직전 답변의 구체적인 표현이나 자소서 문장에 근거한다.
- 지금 빠진 설명 중 가장 중요한 것 하나만 묻는다.
- 이미 답한 질문을 표현만 바꿔 반복하지 않는다.
- 사용자가 하지 않은 일을 했다고 가정하지 않는다.
- 답을 유도하거나 성과 수치를 만들어 내지 않는다.
- 기억이 안 난다는 답변을 계속 추궁하지 않는다. 갈등 사례가 없다고 하면 만들어 내게 요구하지 않는다.

## 6. 답변마다 서버가 하는 일

답변 저장 → 새 정보·정정 사항을 경험 기록에 반영 → 종료·건너뛰기 요청 확인 → 현재 질문의 확인 목적 충족 여부 판단 → 부족하면 꼬리질문, 충분하면 다음 본질문 → 횟수·시간 한도에 도달하면 종료

- 답변마다 AI 호출 한 번으로 확인 상태 갱신 + 다음 행동 판단 + 필요한 꼬리질문을 받는다. 결과는 아래처럼 구조화해서 받는다.

```json
{
  "decision": "follow_up",
  "interviewer": "practical",
  "reason": "결과 확인 방법이 아직 설명되지 않음",
  "basis_answer_id": "A3",
  "target_field": "verification",
  "question": "성능 개선 전후의 차이는 어떤 방법으로 확인했나요?"
}
```

- 서버는 질문 횟수, 존재하는 답변 ID인지, 이미 완료된 항목인지 검사한다. 잘못된 판단이 나오면 사용자가 답변이나 경험 기록을 정정할 수 있다.

## 7. 면접 결과 화면

종합 점수는 넣지 않는다.

1. 질문·답변 기록 (면접관과 질문 목적 포함)
2. 구체화된 경험: 역할·선택 이유·결과 중 새로 설명한 내용
3. 아직 보완할 항목 최대 3개 (해당 답변과 연결)
4. 자소서 수정 제안: 어떤 문장을 왜 바꾸는지 보여 주고 사용자 승인 뒤 반영

## 8. MongoDB에 저장할 것 (최소)

면접 순서, 현재 주제, 질문·답변, 항목별 확인 상태, 종료 사유, 대체 질문 사용 여부.

## 9. 대회 조건에서 오는 기술 조건 (안내서 기준 사실)

- AI 키는 서버만 환경변수 `AI_GATEWAY_API_KEY`로 읽는다. 팀 전체 예산 $10이므로 매 호출에 대화 전체 대신 확인 상태와 최근 답변만 넘긴다. 모델 이름은 공식 Gateway 목록에서 확인한 뒤 정한다.
- 자동 테스트(E2E)는 흐름 하나가 1분 안에 끝나야 하고, 테스트 브라우저에는 카메라·마이크·소리가 없다. 그래서 테스트는 글자 입력으로 답하고, 특정 질문 문구 대신 「답변 저장 → 꼬리질문 또는 다음 주제 → 종료 기록」을 확인한다. 「면접 종료」 버튼으로 테스트를 짧게 끝낸다.
- 질문은 TTS로 읽더라도 화면에 글자로도 보여야 테스트가 확인할 수 있다.
- 음성 전사는 브라우저 내장 기능(크롬, 음성이 구글 서버로 감) 또는 Gateway 전사 모델(예산 사용) 중에서 고른다. 아직 정하지 않았다.
